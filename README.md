# SM BAU microsite

The team's content calendar, built from an Excel workbook. The team uploads the workbook on the Data page, and the
site updates. Analytics will follow in a later phase.

**Stack:** SvelteKit 2 (Svelte 5) on Vercel, exceljs for reading workbooks, and Vercel Blob for storing the
published data. Dependency versions are pinned; upgrade them deliberately.

## How it works

```
Team saves the calendar in Excel → uploads it on the Data page (upload password)
        │
        ▼
read-workbook.ts → parse-calendar.ts (validates against contract.ts)
        │
any errors? ── yes → report shown, site keeps the last valid version
               no  → dataset published to private storage → calendar renders it
```

**The Excel contract is enforced** `src/lib/core/contract.ts` defines the sheet names,
column headers and rules. The code does not repair mistakes in the workbook (wrong years, rows on the wrong
sheet, labels missing from the framework). Instead, the Data page lists exactly what to change in Excel. The
only leniency is for invisible differences: letter case and extra spaces in headers and taxonomy labels.

Until a real workbook is published, the site shows dummy data from the bundled template.

## Project layout

| Path                                    | What it is                                                                                                                     |
| --------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| `src/lib/core/`                         | Framework-free TypeScript: the Excel contract, the parser/validator and calendar view helpers. Most of the logic lives here.   |
| `src/lib/server/`                       | Server-only code: reading the .xlsx, storage (Blob or the local `.data/` folder), passwords/sessions and the calendar service. |
| `src/hooks.server.ts`                   | Sends every request without a valid sign-in to `/login`; adds security headers.                                                |
| `src/lib/components/`                   | Svelte components.                                                                                                             |
| `src/routes/`                           | `/` calendar, `/data` status, upload and Excel rules, `/login`, `/logout`.                                                     |
| `src/lib/assets/calendar-template.xlsx` | Template with dummy data. Generated by `npm run template`; used as sample data and for the download link.                      |
| `tests/`                                | Vitest unit tests for the parser, view helpers and sign-in.                                                                    |

## Local development

```bash
npm install
npm run dev               # http://localhost:5173 (no passwords locally unless you set them in .env)
npm test                  # unit tests
npm run check             # type check
npm run template          # regenerate the template after changing contract.ts or the dummy rows
```

Locally, published data is stored in `.data/` (git-ignored). Delete that folder to go back to sample data.
To try the sign-in locally, copy `.env.example` to `.env` and fill in the three password settings.

## Passwords

There are two shared passwords:

| Setting           | Gives access to                                                                                                                         |
| ----------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| `SITE_PASSWORD`   | Viewing the calendar and the Data page. Give this to the team.                                                                          |
| `UPLOAD_PASSWORD` | Everything above, plus publishing a new workbook. Give this only to whoever maintains the calendar.                                     |
| `AUTH_SECRET`     | Not a password anyone types. A random string of 32+ characters that signs sign-in cookies. Generate one with `openssl rand -base64 48`. |

- Sign-ins last 30 days.
- **Changing a password signs out everyone who used it.** Do this when someone leaves the team. Changing
  `AUTH_SECRET` signs out everyone.
- On Vercel, the site **refuses to run unprotected**: if any of the three settings is missing, too short, or
  the two passwords are the same, every page shows "Site locked" until it's fixed.
- Use long passwords, such as four or five random words. Shared passwords can't be rate-limited per person, so
  their length is the main protection.
- Not covered by the passwords: the downloadable template file, which holds only dummy rows and the BAU
  framework labels, and the site's JavaScript and CSS, which contain no data.

## Deploying to Vercel

1. Push this repository to GitHub and import it in Vercel. No build settings are needed.
2. In the project's **Storage** tab, create a **Blob** store and connect it. Vercel adds `BLOB_READ_WRITE_TOKEN`.
   Data is stored as _private_ blobs.
3. Under **Settings → Environment Variables**, add `SITE_PASSWORD`, `UPLOAD_PASSWORD` and `AUTH_SECRET`, then
   redeploy.
4. Open the site, sign in with the upload password, go to **Data** and publish the calendar workbook.

## Changing the Excel contract

1. Edit `src/lib/core/contract.ts`: add a column to `MONTH_COLUMNS` or update `RULES`.
2. If the new column needs handling, use it in `parse-calendar.ts` and add a test in `tests/parse-calendar.test.ts`.
3. Run `npm run template` and `npm test`.

The Data page's rules table and the template are both generated from `contract.ts`, so they stay in sync.
